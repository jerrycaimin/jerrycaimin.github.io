🔀 网络排障 · 实战笔记

Clash TUN 模式原理与系统代理设置指南
——从一次企业 VPN 冲突说起

TUN 模式一开，整机网络全部瘫痪，连 IDE 里的 AI 对话都断线；关掉 TUN 又用不了透明代理。 本文从原理层面讲清楚 TUN 模式和系统代理的本质区别，并用一次 Clash Verge + 企业安全 VPN（安心连） 的真实冲突案例，给出可复用的排障流程和修复方式。

实战日期：2026-09-03 涉及组件：Clash Verge（mihomo 内核）· macOS Network Extension 适用场景：Clash / 其他基于 TUN 的代理工具 与 任意企业 VPN 客户端冲突 👁

📐先搞清楚：TUN 模式和系统代理不是一回事

很多人把 Clash 的"TUN 模式"和"系统代理"当成同一个东西的两种开法，其实它们工作在完全不同的层级， 互相独立、可以任意组合开关：

对比项系统代理（System Proxy）TUN 模式
工作层级 应用层——写入 macOS 系统偏好设置的 HTTP/HTTPS/SOCKS 代理字段 网络层——创建虚拟网卡（utun），直接接管 IP 数据包
生效范围 只有主动读取系统代理配置的 App 才会走代理（Chrome、Safari 等） 系统级透明代理，任何进程的流量都会被拦截转发，不需要 App 配合
可被检测方式 networksetup -getwebproxy 等标准 API 直接可读，非常容易被第三方工具"发现" 需要检测虚拟网卡 / 路由表 / Network Extension 才能发现，检测成本更高
配置文件字段（Clash Verge） enable_system_proxy enable_tun_mode
典型问题 容易被企业安全软件的"代理合规检测"扫到并报警 容易和其他基于 TUN/VPN 的软件抢路由、抢网段，导致断网
ℹ️
两个开关互相独立、互不依赖——这意味着关掉系统代理不会影响 TUN 模式的实际转发能力， 反之亦然。后面两个真实案例分别对应这两条完全不同的故障路径。

🔬TUN 模式底层原理

开启 TUN 模式后，Clash（mihomo 内核）大致做了这几件事：

① 创建虚拟网卡 通过 macOS 的 Network Extension（NEPacketTunnelProvider）创建一个 utun 接口， 分配一个虚拟 IP（如 utun1024 → 28.0.0.1）
② 抢占路由表（auto-route） 向系统路由表写入指向这个虚拟网卡的路由条目，一般是全局默认路由 0.0.0.0/0，配合 strict-route 决定抢占强度
③ 劫持 DNS（dns-hijack + fake-ip） 把所有 :53 DNS 查询劫持到自己，用 fake-ip-range 网段（默认 198.18.0.1/16）给每个域名分配一个虚拟 IP，不做真实解析
④ 拦截转发 任何流量只要目的地址落在 fake-ip 网段，mihomo 内核就识别出真实域名，按规则匹配代理节点转发
⚠️
问题根源就在这里：第②步"抢占路由"和第③步"fake-ip 网段"， 都可能和另一个同样使用 TUN/VPN 机制的软件冲突——如果对方也声明了同一网段的路由， 两边的路由表项就会打架。

🧨案例一：fake-ip 网段与企业 VPN 路由冲突，导致全局断网

现象
🔴
Mac 上同时装了 Clash Verge（TUN 模式）和公司要求的安心连 VPN。只要打开 TUN， 不是某个连接失败，而是整机网络全部异常——连 VS Code 里跟 AI 助手的对话都报网络错误。 关掉 TUN、改用系统代理，一切正常。
诊断

先确认企业 VPN 的虚拟网卡具体声明了哪些路由：

# 查看安心连的虚拟网卡(utun4)具体路由了哪些网段
netstat -rn -f inet | grep utun4

# 输出：
10.251.1.1         10.251.1.1         UH                  utun4
30.0.0.1/32        10.251.1.1         UGSc                utun4
198.18.0/16        10.251.1.1         UGSc                utun4   ← 就是它！

再看 Clash 当前的 TUN / DNS 配置（-f 参数指向的就是内核实际读取的运行时配置文件）：

tun:
  auto-route: true
  strict-route: true        # 强制抢占，哪怕对方已有更具体路由
  route-exclude-address: []  # 没有任何排除名单
dns:
  enhanced-mode: fake-ip
  fake-ip-range: 198.18.0.1/16  # ← 和安心连撞车了
根因
⚠️
安心连给自己的隧道静态声明了 198.18.0.0/16 这个路由（很多企业 VPN 会复用 IANA 保留的"基准测试"网段做内部用途），而 Clash 的 fake-ip DNS 机制默认恰好也用同一个网段 给所有域名分配虚拟 IP。两个 TUN 接口对同一网段抢路由表项，导致 Clash 的 DNS 伪装解析被安心连的路由 劫持打穿——所有依赖域名解析的连接全部失败，这就是"全局断网"而非"部分流量异常"的原因。
修复

在 Clash Verge 的全局覆盖模板（不会被订阅更新覆盖，持久生效）里改两处：

# ~/Library/Application Support/io.github.clash-verge-rev.clash-verge-rev/profiles/Merge.yaml
profile:
  store-selected: true

# 换成不和已知 VPN 冲突的网段
dns:
  fake-ip-range: 28.0.0.1/16

# 降低路由抢占强度，给对方留活路
tun:
  strict-route: false

改完后在 Clash Verge 里刷新一次订阅（或直接重启 App），让覆盖生效。

验证结果
检查项结果
TUN 接口分到 28.0.0.1，与企业 VPN 网段不再重叠
路由表198.18.0/16 仍归企业 VPN，Clash 用 28.0.0.0/16，各走各的
DNS 解析正常返回 fake-ip，0.08 秒
SSH / IDE 网络恢复正常

🕵️案例二：企业安全软件报"检测到第三方代理"

现象

修好 TUN 冲突之后，企业安全软件（安心连）自带的"一键诊断"报了另一项异常： "网络代理——检测到第三方网络代理，请及时去除代理"，并提供了一个"一键修复"按钮。

⚠️
不建议直接点企业安全软件自带的"一键修复"——那是个黑盒，不确定它除了清代理设置， 还会不会做别的事情（比如强制杀掉相关进程、修改网络服务优先级，甚至直接退出 Clash）。 更稳妥的做法是先自己定位到底是哪个开关触发的检测，手动关掉，风险完全可控。
诊断思路

关键线索是措辞——报的是"网络代理"而不是"VPN检测"。国内政企安全软件做代理合规检测， 几乎都是最简单直接的方式：调用 macOS 标准 API 读取"系统偏好设置 → 网络 → 代理"配置， 而不会去深挖底层的虚拟网卡（那通常归到另一个检测项）。验证一下：

# 用和企业安全软件同样的标准 API 自己先查一遍
networksetup -getwebproxy Wi-Fi
networksetup -getsocksfirewallproxy Wi-Fi

# 输出：
Enabled: Yes
Server: 127.0.0.1
Port: 7897   ← Clash Verge 系统代理模式的默认混合端口

再确认"系统代理"和"TUN 模式"在 Clash Verge 自身配置里是不是两个独立开关：

# ~/Library/Application Support/io.github.clash-verge-rev.clash-verge-rev/verge.yaml
enable_tun_mode: true
enable_system_proxy: true   ← 就是它被读到了
修复
✅
在 Clash Verge 里只关闭"系统代理"这一个开关，TUN 模式继续保持打开。 因为 TUN 在网络层直接接管流量，完全不依赖系统偏好设置里的代理配置——关掉系统代理， 企业安全软件检测通过，Clash 的实际转发能力（TUN）丝毫不受影响。

日常固定配置：TUN 模式开、系统代理关。已实测确认企业安全软件诊断通过， 且代理功能、独立的 SSH SOCKS5 隧道等均不受影响。

🧭通用排查流程（适用于任意"Clash TUN + 其他 VPN"冲突）

换了别的企业 VPN 客户端，或者 Clash 换了内核版本再遇到类似问题，可以照这个顺序走：

① 先分清是"全局断网"还是"部分请求失败" 全局断网（含 DNS 解析类应用全灭）→ 大概率是 fake-ip 网段或 DNS 劫持冲突； 只是个别域名/IP 连不上 → 大概率是普通的路由排他没配置好
② 查两边虚拟网卡各自声明了哪些网段 ifconfig | grep -E 'utun|inet' 找出所有 utun 接口； netstat -rn -f inet | grep utunX 逐个看路由
③ 对比 Clash 的 fake-ip-range 是否落在对方网段内 凡是两边网段有交集，无脑换成对方肯定没用到的网段（如 28.0.0.1/16）
④ 把 strict-route 关掉，降低抢占强度 如果对方声明了具体的内部网段（而不是整个默认路由），配合 route-exclude-address 显式排除，让对方的流量继续走自己的隧道
⑤ 改动写进 Merge.yaml 而不是运行时配置 运行时的 clash-verge.yaml 每次刷新订阅都会被重新生成， 直接改它会白改；profiles/Merge.yaml 是持久化覆盖层，改这里才不会被订阅更新冲掉
一键诊断脚本（可直接复制运行） 
#!/bin/bash
# 快速摸清当前所有 utun 接口的归属和路由，定位冲突网段
echo '=== 所有 utun 接口 ==='
for i in {0..9}; do
  ifconfig utun$i 2>/dev/null | grep -E 'inet|mtu' && echo "  ↑ utun$i"
done

echo '=== 完整 IPv4 路由表 ==='
netstat -rn -f inet

echo '=== Clash 当前 tun/dns 配置 ==='
CONF="$HOME/Library/Application Support/io.github.clash-verge-rev.clash-verge-rev/clash-verge.yaml"
grep -A 10 '^tun:' "$CONF"
grep -A 15 '^dns:' "$CONF"

echo '=== 系统代理是否被写入(企业安全软件常查这个) ==='
networksetup -getwebproxy Wi-Fi
networksetup -getsocksfirewallproxy Wi-Fi

📌 结论总结

  • TUN 模式和系统代理是两套独立机制：前者在网络层接管数据包， 后者只是写入 macOS 系统偏好设置的应用层配置，互不依赖，可以分别开关排查
  • "开 TUN 就全局断网"的典型根因：Clash 的 fake-ip-range 默认网段（198.18.0.0/16）和某些企业 VPN 内部复用的网段撞车， 导致 DNS 伪装解析机制被对方路由劫持打穿
  • 修复思路：换一个双方都没用到的 fake-ip 网段（如 28.0.0.1/16）， 关闭 strict-route，改动写进 Merge.yaml 持久化覆盖层
  • "被安全软件报第三方代理"的典型根因：对方多半只检测标准的 macOS 系统代理设置，而不是 TUN 虚拟网卡；关掉"系统代理"开关、保留 TUN 模式即可通过检测
  • 日常推荐配置：TUN 模式常开、系统代理常关——两者组合下企业安全软件 检测通过，Clash 的实际代理转发能力完全不受影响
  • 安全提示：遇到企业安全软件的"一键修复"按钮，优先自己手动定位并关闭 对应开关，而不是直接点黑盒修复，避免它顺带做了预期之外的操作
