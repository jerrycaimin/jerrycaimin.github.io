一、为什么用了 Lance 还要用 JuiceFS
背景 Lance 格式本身可以直接落在 S3 对象存储上。那为什么要在中间加一层 JuiceFS？ 答案不是"因为 Lance 需要"，而是"因为数据分布问题和 GPU 空转问题，没有 JuiceFS 解决不了"。

🌐 多云 / 多 IDC 数据分布

数据跨阿里云、腾讯云、火山云及自有 IDC 分布，有时甚至分布在不同城市。 S3 只能走 TCP，在跨 IDC 场景下延迟高、毛刺严重；GPU 节点之间走 RDMA， 但存储网络与计算网络不在同一平面，需要经过多层交换机。

跨 IDC 延迟 TCP vs RDMA S3 毛刺

🔥 提前预热，消灭 GPU 空转

GPU 任务启动时若从远端实时拉取数据，延迟可达数十秒，导致 GPU 空转。 GPU 空转几十秒的成本远高于存储加速投入。

训练集（trainlist）已知要读哪些数据、哪些帧，JuiceFS Cache Group 可将 GPU 本地 NVMe 盘池化，在任务启动前将数据预热到本地，实现近零等待， 甚至节省高性能共享存储的带宽开销。

Cache Group 预热 NVMe 池化 trainlist 已知读集
"你可以查一下，像腾讯云，它的 GPU 之间走 RDMA，但存储面跟算法那边的网络不是一个网络， 经过很多轮交换机……S3 只能 TCP，非常慢，一旦抖动起来，性能毛刺非常厉害，天天被投诉。" —— 客户方原话

📊 数据生产 vs 训练 IO 对比

数据生产（数据闭环）是顺序读高并发场景，IO 强度远高于训练。 训练是点查场景，但数据生产对吞吐要求更极致。 两个场景都需要 JuiceFS，理由不同但同等重要。

数据生产：顺序读高并发 训练：点查 + 预热

⚙️ JuiceFS 富客户端的价值

  • clip 不打散：同一份 clip 数据保持局部性，clip 间可乱序，clip 内不拆散
  • 业务 SDK 封装：数据校验、QPS 限流、倾斜检测均在客户端层实现
  • 后端可控：TiKV 触发流控时，可通过客户端限速保护集群
  • 非标玩法：Python SDK、OpenZFS 管理面都可以自己搓
"因为用 JuiceFS，它是一个重客户端的工具，我所有的很多非标、或者说很多业务属性的东西， 都在客户端来做完。比方说我们在训练里面有 clip 概念——你不希望一份数据里面的东西拆散， 但是可以 clips 之间打散……不在客户端做，就没有任何地方可以帮你做这个事情。" —— 客户方原话
三、为什么选 Lance 列式存储，而非 LMDB 行式存储
✅ Lance（列式）
  • 列裁剪，只读所需列（5%～10%）
  • 同列类型一致，压缩比极高
  • 原生向量索引（HNSW 等）
  • 标量 + 向量联合检索
  • 非侵入式元数据，不改原始文件
  • 列级热更新，不需重写全表
VS
❌ LMDB（行式 KV）
  • 读一行 = 读所有列，读放大严重
  • 行式压缩效率低（混合类型）
  • 无原生向量检索能力
  • 仅标量点查，无相似度搜索
  • 数据打包侵入原始格式
  • 改一列属性需重写全量文件

📐 标量检索

每一帧都有离散型标注属性：天气（晴/雨/雪）、光照、场景类型等，用 int/bool/long 表示。 列式存储下同列类型一致，压缩比极致——同等数据量可节省一半以上存储。

例：weather_type 列全是 0/1/2 整数，列式压缩后几乎不占空间；行式则每行都要携带完整 JSON。

压缩比 2x～5x+ 精确过滤

🔍 向量检索（embedding 相似度）

大模型对每一帧提取 embedding（128/256/768 维），记录该帧与各类场景的相似度。 向量检索即"模糊版标量查询"，用于业务世界观升级后的模糊 double-check： 例如从"雨天/非雨天"细化到"大雨/中雨/太阳雨"时，用向量召回辅助人工复核。

embedding 相似度 HNSW 索引 标量 + 向量联合

🏗️ Lance vs LanceDB：关系厘清

Lance：一种列式数据格式（类比 Parquet），可存在本地磁盘或对象存储上。

LanceDB：基于 Lance 格式的客户端 SDK 层，提供 Python/Java/Go 包及检索引擎能力（类比 Spark 之于 Parquet）。 商业版支持上万列、服务端检索引擎；社区版已支持 50 亿行 POC，目标千亿行。

推荐客户端：算法侧极度推荐 pylance（Python SDK），Rust 包难以推动，Go 包内部工具侧用。

pylance 极度推荐 fragment/segment ≈ JuiceFS chunk 上万列（商业版） 千亿行目标

📦 非侵入式元数据设计

Lance 不改写原始文件（mcap、点云、PNG 等），只在数据上追加一层元数据记录。 原始数据可通过 URL 软链接形式引用对象存储路径，Lance 文件本体保持轻量。

真正频繁改写的是标注数据——今天把雨天分类细化，只需修改对应列， 无需重写全量数据。这是选择列式的另一个关键原因。

四、为什么选 JuiceFS 而非 Alluxio
Alluxio 的核心缺陷（客户实测结论） Alluxio 是一个纯加速层，无法做到"用户主动控制预热和淘汰"。 在大规模训练和数据生产场景，这是致命短板。
对比维度 JuiceFS Alluxio（社区版）
产品定位 控制面 + 完整文件系统，可管控后端存储 纯缓存加速层，无后端管控能力
主动预热 用户自定义预热时机和内容（trainlist 驱动） 被动预热，读到才加载，时机不可控
缓存淘汰（evict） 支持主动 evict：数据跑完即清理，腾出空间 仅 LRU，缓存只增不减，容量无上界
非 K8s 场景 支持裸金属、单机、多种部署形式 主要面向 K8s 容器层，非容器场景能力弱
业务 SDK 封装 富客户端，可在挂载点上封装业务 SDK 无法暴露给算法层定制 SDK
QoS / 流量治理 客户端级、token 级 QoS；可在流控时限速保护 TiKV 无法感知后端状态，流控失效时无保护
POSIX 语义完整性 完整支持 atime/mtime 等标准语义 不完整，上层业务难以依赖标准语义
横向管理面 可作为多套存储后端的统一控制面 无横向管控能力

⚡ Alluxio 的 evict 问题

Alluxio 依赖 LRU 被动淘汰——缓存满了才触发，告诉你"要加机器"。 但训练任务的数据是有生命周期的：这一轮跑完的数据下一轮不会再用， 应该立即主动清理。

如果无法主动 evict，缓存层会持续膨胀，最终成为运维负担。

🏗️ JuiceFS 作为控制面的价值

JuiceFS 不只是"加速"，它是一个具备后端感知能力的控制面：

  • 感知 TiKV 流控信号，客户端主动降速
  • 在挂载点上架一层业务 SDK（数据分布检测、校验、限流）
  • 跨多套后端统一纳管（替代或补充 Alluxio 能力）
  • QoS 精细化：单客户端级，企业版支持 token 级批量限速
"站在我的角度，JuiceFS 是一个控制面的东西，Alluxio 只是一个加速层。 Alluxio 没办法穿透给算法层，因为它不是一个完整的客户端对接后端的产品， 控制不了后端……我们用 JuiceFS 可以做那些 OpenZFS 的各种各样的管理面，自己搓都可以。" —— 客户方原话
五、实战案例：数据闭环与模型训练的真实做法
说明 以下内容来自与某头部智驾公司技术负责人的深度访谈，还原他们实际落地的 Lance + JuiceFS 工程实践，非泛化描述。
5.1  数据闭环（数据生产）

🚗 原始数据从哪来，怎么存

车辆采集的原始数据包括 mcap 文件（ROS 消息捕获）、激光雷达点云（.pcd）、摄像头 PNG 帧， 存放在阿里云 OSS / 腾讯云 COS / 自有 IDC 的对象存储中。原始文件本身不被修改。

JuiceFS 将多云/多 IDC 的对象存储统一挂载为同一个 POSIX 目录树， 标注工具链只需访问 JuiceFS 挂载点，无需感知底层是哪朵云。 跨云访问的延迟和稳定性问题由 JuiceFS 的缓存和预热机制在客户端层面解决。

mcap · 点云 · PNG 阿里云 + 腾讯云 + IDC JuiceFS 统一挂载点

📋 Lance 标注表的真实结构

Lance 标注表每行对应一个视频帧（或一个数据包），列分三类：

  • 标量列：weather_type: int8（1=雨天，2=晴天，3=太阳雨…）、scene_type: int8、speed_range: float32 等。全是整型/布尔/浮点，同列类型一致，列式压缩比极高。
  • 向量列：大模型对每帧提取的 embedding，128/256/768 维 float32 数组，支持 HNSW 向量检索。
  • 元数据/路径列：raw_path: string（软链接指向原始文件在对象存储上的路径）、timestamp: int64。点云可以整列存储（一列 = 一个雷达传感器的数据包）。

一张大宽表可有几百到上千列（团队持续追加新标注维度，不需要重写旧数据）， 当前 POC 已验证 50 亿行，奔着千亿行目标。 按 fragment 切片控制单文件大小（类似 JuiceFS 的 chunk 概念）。

标量列（压缩比极高） 向量列（embedding） 元数据软链接 50 亿行 POC 验证

🔍 数据挖掘：标量 + 向量联合查询

数据闭环的核心操作是从海量帧中筛选出符合训练需求的子集，全部通过 pylance Python SDK 完成：

# 场景1：标量精确过滤——筛选雨天城市道路场景
df = tbl.search().where("weather_type = 1 AND scene_type = 3").to_pandas()

# 场景2：向量相似度检索——找与大雨场景相似的帧
results = tbl.search(query_vec, query_type="vector").metric("cosine").limit(10000).to_pandas()

# 场景3：标量 + 向量联合——业务世界观升级时做模糊 double-check
results = tbl.search(query_vec).where("weather_type IN (1,3)").limit(5000).to_pandas()

为什么要联合检索？ 业务世界观在持续演进：一开始只有"雨天/非雨天"二分， 随着模型迭代要细化为"大雨/中雨/太阳雨"。标量标注是人/机器标的确定值， 向量 embedding 提供相似度模糊判断，两者结合才能覆盖世界观升级时的灰色地带。

pylance Python SDK（极度推荐） 标量精确 + 向量模糊联合 世界观升级迭代友好

♻️ 闭环写回：只改列，不改原始文件

标注属性定义变更时（如把"雨天"细化为三级），只需修改 Lance 表中对应的列， 无需重写原始 mcap/点云文件，也无需重写其他列。 Lance 列级热更新让数据闭环的迭代成本极低——这是相比 LMDB 行式存储的核心优势之一。

数据闭环跑完一个批次后，对应数据在 JuiceFS 缓存层主动 evict， 腾出 NVMe 空间给下一个批次，避免缓存无限膨胀（Alluxio 没有这个能力）。

列级热更新 主动 evict，缓存不膨胀
"标注数据可能我今天识别一个产品，明天我需要细化，那么疯狂读改写，那就非常适合用 Lance 了。 比方说我觉得这个车它应该有低速高速，但是明天你要是对这个低速高速的定义给我改了， 那我以前就得把所有文件删掉重改。但我现在只要改那一列，加一列，把旧那一列干掉就可以了。" —— 客户方原话
5.2  模型训练

📦 训练集生成：从 Lance 到 trainlist

训练集生成过程：从 Lance 表中按条件筛选出目标帧的 raw_path 列， 生成一个 trainlist（文件路径列表），每一行指向 JuiceFS 挂载点下的原始帧文件。

训练只读帧，不读整段视频。 一段 mcap 视频可能几个 GB， 训练只需要其中的某些帧（PNG 图片）。Lance 的列裁剪让训练框架精确知道读哪些帧、 读哪几列标注属性（只读 5% 的列），大幅降低无效 IO。

trainlist = 帧路径列表 只读帧，不读整段视频 列裁剪 → 只读 5% 的列

🔥 预热机制：GPU 启动前数据已就位

这是 JuiceFS 在训练场景中最核心的价值——消灭 GPU 空转：

  1. 训练任务提交时，同步触发预热任务
  2. 预热任务读 trainlist，通过 JuiceFS 将所有待训练帧文件下载到 GPU 节点本地 NVMe 盘（Cache Group 池化多块 NVMe）
  3. 预热完成后，训练任务才正式启动，直接读本地 NVMe，时延 <1ms
  4. 训练批次结束，主动 evict 该批次缓存，腾出空间

为什么性价比极高？ 多云/多 IDC 场景下，GPU 跨云直读 S3 每次请求延迟达 80-100ms， 且 GPU 机器之间走 RDMA 但存储网络需经过多层交换机，抖动严重。 预热后本地 NVMe 延迟 <1ms，GPU 利用率从不足 50% 提升到接近 100%。 GPU 空转 30 秒的成本（A100/H100 按小时计费）远超整套存储加速投入。

GPU 空转 30s 成本 >> 存储投入 NVMe 本地读 <1ms 跨云 S3 延迟 80-100ms → 消灭

📎 clip 局部性保证：训练质量的工程基础

自动驾驶训练中，时序模型（行为预测、BEV 感知等）需要同一 clip 的连续帧在同一个 batch 中出现， 不能被打散给不同 worker。

clip 定义：一段连续行驶视频片段（通常几秒到几十秒）。 训练时 clip 之间可以打散、随机排列，但 clip 内的帧必须连续不拆散。

这个逻辑在 S3 层或 Alluxio 层无法实现。JuiceFS 作为富客户端， 在客户端层面保证 clip 内的帧在 Cache Group 上连续存储， 预热时按 clip 为单位批量拉取，训练框架只管从挂载点读，无需感知底层分布。

clip 内不打散 clip 间可乱序 富客户端实现，S3/Alluxio 做不到
"我知道我要读哪些数据，甚至知道读这些数据的哪一帧，那我提前把它预热过来…… 我的 GPU 下面已经有本地盘了，我的通信我连存储高性能存储都可以省掉很大一部分。 如果做不到非常极致的场景，那么就证明它们的数据 IO 是一定出问题了。" —— 客户方原话
