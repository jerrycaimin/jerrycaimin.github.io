一、为什么用了 Lance 还要用 JuiceFS
背景 Lance 格式本身可以直接落在 S3 对象存储上。那为什么要在中间加一层 JuiceFS？ 答案不是"因为 Lance 需要"，而是"因为数据分布问题和 GPU 空转问题，没有 JuiceFS 解决不了"。

🌐 多云 / 多 IDC 数据分布

数据跨阿里云、腾讯云、火山云及自有 IDC 分布，有时甚至分布在不同城市。 S3 只能走 TCP，在跨 IDC 场景下延迟高、毛刺严重；GPU 节点之间走 RDMA， 但存储网络与计算网络不在同一平面，需要经过多层交换机。

跨 IDC 延迟 TCP vs RDMA S3 毛刺

🔥 提前预热，消灭 GPU 空转

GPU 任务启动时若从远端实时拉取数据，延迟可达数十秒，导致 GPU 空转。 GPU 空转几十秒的成本远高于存储加速投入。

训练集（trainlist）已知要读哪些数据、哪些帧，JuiceFS Cache Group 可将 GPU 本地 NVMe 盘池化，在任务启动前将数据预热到本地，实现近零等待， 甚至节省高性能共享存储的带宽开销。

Cache Group 预热 NVMe 池化 trainlist 已知读集
"你可以查一下，像腾讯云，它的 GPU 之间走 RDMA，但存储面跟算法那边的网络不是一个网络， 经过很多轮交换机……S3 只能 TCP，非常慢，一旦抖动起来，性能毛刺非常厉害，天天被投诉。" —— 客户方原话

📊 数据生产 vs 训练 IO 对比

数据生产（数据闭环）是顺序读高并发场景，IO 强度远高于训练。 训练是点查场景，但数据生产对吞吐要求更极致。 两个场景都需要 JuiceFS，理由不同但同等重要。

数据生产：顺序读高并发 训练：点查 + 预热

⚙️ JuiceFS 富客户端的价值

  • clip 不打散：同一份 clip 数据保持局部性，clip 间可乱序，clip 内不拆散
  • 业务 SDK 封装：数据校验、QPS 限流、倾斜检测均在客户端层实现
  • 后端可控：TiKV 触发流控时，可通过客户端限速保护集群
  • 非标玩法：Python SDK、OpenZFS 管理面都可以自己搓
"因为用 JuiceFS，它是一个重客户端的工具，我所有的很多非标、或者说很多业务属性的东西， 都在客户端来做完。比方说我们在训练里面有 clip 概念——你不希望一份数据里面的东西拆散， 但是可以 clips 之间打散……不在客户端做，就没有任何地方可以帮你做这个事情。" —— 客户方原话
三、为什么选 Lance 列式存储，而非 LMDB 行式存储
✅ Lance（列式）
  • 列裁剪，只读所需列（5%～10%）
  • 同列类型一致，压缩比极高
  • 原生向量索引（HNSW 等）
  • 标量 + 向量联合检索
  • 非侵入式元数据，不改原始文件
  • 列级热更新，不需重写全表
VS
❌ LMDB（行式 KV）
  • 读一行 = 读所有列，读放大严重
  • 行式压缩效率低（混合类型）
  • 无原生向量检索能力
  • 仅标量点查，无相似度搜索
  • 数据打包侵入原始格式
  • 改一列属性需重写全量文件

📐 标量检索

每一帧都有离散型标注属性：天气（晴/雨/雪）、光照、场景类型等，用 int/bool/long 表示。 列式存储下同列类型一致，压缩比极致——同等数据量可节省一半以上存储。

例：weather_type 列全是 0/1/2 整数，列式压缩后几乎不占空间；行式则每行都要携带完整 JSON。

压缩比 2x～5x+ 精确过滤

🔍 向量检索（embedding 相似度）

大模型对每一帧提取 embedding（128/256/768 维），记录该帧与各类场景的相似度。 向量检索即"模糊版标量查询"，用于业务世界观升级后的模糊 double-check： 例如从"雨天/非雨天"细化到"大雨/中雨/太阳雨"时，用向量召回辅助人工复核。

embedding 相似度 HNSW 索引 标量 + 向量联合

🏗️ Lance vs LanceDB：关系厘清

Lance：一种列式数据格式（类比 Parquet），可存在本地磁盘或对象存储上。

LanceDB：基于 Lance 格式的客户端 SDK 层，提供 Python/Java/Go 包及检索引擎能力（类比 Spark 之于 Parquet）。 商业版支持上万列、服务端检索引擎；社区版已支持 50 亿行 POC，目标千亿行。

推荐客户端：算法侧极度推荐 pylance（Python SDK），Rust 包难以推动，Go 包内部工具侧用。

pylance 极度推荐 fragment/segment ≈ JuiceFS chunk 上万列（商业版） 千亿行目标

📦 非侵入式元数据设计

Lance 不改写原始文件（mcap、点云、PNG 等），只在数据上追加一层元数据记录。 原始数据可通过 URL 软链接形式引用对象存储路径，Lance 文件本体保持轻量。

真正频繁改写的是标注数据——今天把雨天分类细化，只需修改对应列， 无需重写全量数据。这是选择列式的另一个关键原因。

四、为什么选 JuiceFS 而非 Alluxio
Alluxio 的核心缺陷（客户实测结论） Alluxio 是一个纯加速层，无法做到"用户主动控制预热和淘汰"。 在大规模训练和数据生产场景，这是致命短板。
对比维度 JuiceFS Alluxio（社区版）
产品定位 控制面 + 完整文件系统，可管控后端存储 纯缓存加速层，无后端管控能力
主动预热 用户自定义预热时机和内容（trainlist 驱动） 被动预热，读到才加载，时机不可控
缓存淘汰（evict） 支持主动 evict：数据跑完即清理，腾出空间 仅 LRU，缓存只增不减，容量无上界
非 K8s 场景 支持裸金属、单机、多种部署形式 主要面向 K8s 容器层，非容器场景能力弱
业务 SDK 封装 富客户端，可在挂载点上封装业务 SDK 无法暴露给算法层定制 SDK
QoS / 流量治理 客户端级、token 级 QoS；可在流控时限速保护 TiKV 无法感知后端状态，流控失效时无保护
POSIX 语义完整性 完整支持 atime/mtime 等标准语义 不完整，上层业务难以依赖标准语义
横向管理面 可作为多套存储后端的统一控制面 无横向管控能力

⚡ Alluxio 的 evict 问题

Alluxio 依赖 LRU 被动淘汰——缓存满了才触发，告诉你"要加机器"。 但训练任务的数据是有生命周期的：这一轮跑完的数据下一轮不会再用， 应该立即主动清理。

如果无法主动 evict，缓存层会持续膨胀，最终成为运维负担。

🏗️ JuiceFS 作为控制面的价值

JuiceFS 不只是"加速"，它是一个具备后端感知能力的控制面：

  • 感知 TiKV 流控信号，客户端主动降速
  • 在挂载点上架一层业务 SDK（数据分布检测、校验、限流）
  • 跨多套后端统一纳管（替代或补充 Alluxio 能力）
  • QoS 精细化：单客户端级，企业版支持 token 级批量限速
"站在我的角度，JuiceFS 是一个控制面的东西，Alluxio 只是一个加速层。 Alluxio 没办法穿透给算法层，因为它不是一个完整的客户端对接后端的产品， 控制不了后端……我们用 JuiceFS 可以做那些 OpenZFS 的各种各样的管理面，自己搓都可以。" —— 客户方原话

核心结论 Lance 解决"如何高效存储和检索多模态标注数据"（列裁剪、标量+向量联合索引、非侵入元数据）； JuiceFS 解决"数据在哪里、怎么快速拿到"（多云统一、主动预热、GPU 空转消除、富客户端控制）。 两者不是竞争关系，而是互补的不同层次。
